**Lancer Nexus ** **Download** ** ** **Server**  
The Download Server publishes signed manifests and immutable client/game-data artifacts for Windows and Linux.  
**Responsibilities**  
- Serve channel- and platform-specific manifests  
- Publish immutable artifacts addressed by hash  
- Support stable, beta, nightly and internal channels  
- Expose health and readiness endpoints  
- Integrate with the GitHub Actions release pipeline  
- Keep signing operations separate from public artifact serving  
The Download Server does not authenticate game sessions and does not replace the Gateway.

## Offline release publisher

`Publisher/` is a separate command-line project. It accepts an already signed manifest, a public trust root and artifacts staged under `sha256/<prefix>/<sha256>`. It verifies the signature/schema/target and each artifact's size and SHA-256, installs hash-addressed objects without replacing existing content, and only then atomically activates the channel manifest. It rejects symbolic links and other reparse points in source, artifact, manifest and audit paths to prevent configured roots from escaping through filesystem aliases. Before activation it writes a durable `prepared` audit record and stages a durable `activated` record. The manifest replacement is the commit point; the staged record is renamed into the audit log immediately afterward. If the process stops between those operations, the next publication reconciles the pending record against the active manifest payload digest before advancing the channel. Store `--audit-root` outside the public manifest and artifact roots and retain it with deployment-level append-only controls. It contains no signing implementation or private key.

Build with `dotnet build Publisher/Publisher.csproj -c Release`. Publish releases with `--manifest FILE --trust-root FILE --source-root DIR --artifact-root DIR --manifest-root DIR --audit-root DIR`. Publish a pre-signed TUF root successor with `--root-metadata FILE --trust-root FILE --manifest-root DIR --audit-root DIR`; add `--root-chain-state FILE` to replay the current chain from the bootstrap trust root before publishing later root versions. Publish TUF metadata with `--tuf-timestamp FILE --tuf-snapshot FILE --tuf-targets FILE --trust-root FILE --artifact-root DIR --manifest-root DIR --audit-root DIR`. Add `--tuf-delegated-dir DIR` when the snapshot references delegated roles; place each referenced role file under that directory using `<version>.<role>.json` for consistent snapshots or `<role>.json` otherwise. The publisher verifies every referenced delegated signature, version, digest, inherited target scope and role trust before checking the effective target set against already-published content. It writes delegated roles, snapshot and targets before atomically activating timestamp last. Add `--root-chain-state FILE` to replay the current root chain before verifying metadata. Root and role publication keep prepared/activated audit records outside public roots. Keep signing in a restricted release job or offline signer; expose only the resulting signed metadata and immutable artifacts to the publisher. Serve artifact storage behind a CDN with origin pass-through for `Range` and conditional requests, immutable caching for hash URLs, and revalidation for manifests. Production identity, audit retention, CDN configuration and key rotation still require deployment-specific setup.

## Runtime

The .NET 10 host exposes `/health/live`, `/health/ready`, signed channel manifests at `/v1/channels/{channel}/manifest`, bootstrapper manifests, versioned root metadata at `/v1/metadata/root/{version}`, TUF roles at `/v1/metadata/{rolePath}`, and immutable artifacts at `/v1/artifacts/{first-two-sha256-characters}/{sha256}`. Root files are read from `<ManifestRoot>/root/<version>.json`; TUF roles are read from `<ManifestRoot>/metadata/`. Timestamp uses `timestamp.json`; consistent-snapshot roles use `{version}.<rolePath>.json`, including nested delegated roles such as `5.delegates/content.json`; other roots use `<rolePath>.json`. Both metadata endpoints apply the same size limit, content-derived ETag, `no-cache` revalidation and configured-root symlink/reparse-point checks as manifests. The role endpoint accepts safe role paths and positive canonical versions. Artifacts support byte ranges, SHA-256 ETags, conditional `304` responses, one-year immutable caching, and content-length reporting. Manifests use a content-derived ETag and `no-cache` so clients revalidate them; the response uses the same byte snapshot used to calculate the ETag. Manifest, root metadata and artifact paths that escape their configured roots through symbolic links or reparse points are rejected. Invalid hash prefixes and unsafe channel/platform/architecture segments are rejected.

Configure `Download:ManifestRoot` and `Download:ArtifactRoot`. Store manifests as `<root>/<channel>/<platform>-<architecture>.json`, top-level TUF role envelopes under `<root>/metadata/`, and artifacts as `<root>/sha256/<prefix>/<sha256>`. TUF target names use `<channel>/<platform>-<architecture>.json` for manifests and `artifacts/<prefix>/<sha256>` for packages. The service never accepts arbitrary filesystem paths or manifest URLs. Signature generation and publication stay outside this public serving process.

Run endpoint and signed DownloadServer-to-Updater client artifact integration tests with `dotnet test Tests/Download.Tests.csproj -c Release`. The CI workflow checks out the Updater test seam at a pinned commit so these tests exercise both services without adding a runtime dependency between them. CI builds and format-checks the standalone Publisher as part of the Download test pipeline.
